# 微信登录、数据库密钥生命周期与 AIWC 连接流程调查

调查日期：2026-10-14 至 2026-10-15。目标：macOS arm64 微信 4.1.15，构建号 270134。使用相邻 `rea` 项目的 REA 6.4.0 元数据证据、限定范围 ARM64 指令分析，以及用户发起的本机只读探针。

**本轮确认了一条无需重新登录的数据库密钥获取路径。** 微信已经打开的数据库保留着经过 XOR 混淆的派生密钥。研究探针在微信保持运行时找到这些材料，同一账号的 10 个数据库均通过首页解密检查，以及首页、第二页、末页的 HMAC 校验；这次扫描耗时 0.435 秒。

这支持把 AIWC 的常规体验改为「连接微信 → 阅读」，并在安全存储可用、对应数据库没有换密钥时，让后续启动直接复用凭据。用户不必理解或手动管理密钥。**后台仍需要解密材料；扫码登录凭据不能直接代替它。** 本轮只完成研究原型与页面级验证，没有接入生产读取器，也没有证明普通 SIP 开启环境下首次连接可以免授权。

> **REA 分支实现更新（2026-10-15）：** §1–§7 保留接入前的研究快照，文中的“当前源码”“未接入”“下一步”和原工作区检查数量均指当时状态。REA 已将只读 codec、账号私有每库凭据、数据库先保存与独立图片补齐接入生产路径；最新实现、真实 reader 验证与未解决边界见 §8 及 [ARCHITECTURE §13、§18](ARCHITECTURE.md)。历史登录 helper 的调查保留作为证据，该 helper 及自动重启捕获已从 REA 生产路径移除。

## 1. 本轮实际做了什么

微信业务库身份沿用 [上一轮存储调查](WECHAT-STORAGE-RESEARCH.md)：

```text
/Applications/WeChat.app/Contents/Resources/wechat.dylib
SHA-256: a1709ba62cae1b8b2705137980e23983ed42dc88affe774c4442488b82b007fe
arm64 UUID: 8ACF7A2F-517C-32B4-9DFB-47E8849CD444
arm64 切片起点: 184614912 / 0x0b010000
```

只读运行探针检查进程加载的业务库 UUID，外围运行器检查磁盘业务库摘要，然后读取加载信息、数据库上下文和有限的候选材料。数据库只读取三个固定页；首页仅解密 32 字节来检查 SQLite 结构，其余页面只计算密文完整性校验。没有查询聊天正文，没有输出或保存任何真实密钥、登录 Token、账号目录名或 wxid。

没有退出登录、重启微信、注入代码、修改线程寄存器、挂登录断点、修改微信签名或写入微信目录。研究用 C 探针由本机编译，仅对这个新生成的研究可执行文件使用项目现有 debugger entitlement 做 ad-hoc 签名；它不在 AIWC 的打包资源中。

本机证据目录：`/Users/miaoyijun/Downloads/Paper&Project/rea-investigations/wechat-login-keys-4.1.15-20261014/`。其中的 `investigation-ledger.json` 区分观察、源码事实、推断和未知项；`artifact-manifest.json` 固定材料摘要。探针输出只包含匿名匹配结果、数量、耗时和内存范围统计。

## 2. 登录鉴权与本地解密分别负责什么

| 材料或过程 | 本轮证据 | 对 AIWC 的意义 |
|---|---|---|
| 微信扫码、手机确认、自动登录 | 客户端包含二维码检查、手动鉴权与自动鉴权线索；自动鉴权字段有本地 MMKV 读写调用链 | 让微信自身建立账号会话；本轮未恢复完整登录协议 |
| `mmkv_key_auto_auth_key` | 常量地址 `0x983d577`，指针表槽位 `0xa056618`，读写者分别调用 MMKV 包装器 | 是自动鉴权材料的线索；没有证据证明它等于数据库密钥，也没有读取实际值 |
| 数据库输入口令 | WCDB/SQLCipher 上下文复制输入后做 XOR 混淆，派生完成后可覆盖并释放 | 登录时截获可能拿到这一层，但不能假设登录后一直保留 |
| 每个数据库的派生密钥 | 当前运行进程中已找到，能独立通过各库页面校验 | 是此次无需重新登录路径的实证基础 |
| 图片密钥 | AIWC 有缓存推导与进程扫描回退 | 应作为独立能力补充，不能阻塞文字聊天 |
| AIWC iLink 扫码会话 | 源码调用 `get_bot_qrcode` / `get_qrcode_status`，保存 `bot_token`，用于机器人通道 | 当前接口没有桌面历史数据库解密材料或全部个人历史读取能力 |

因此，「扫码后连接」可以是产品上的统一体验，但在当前本地数据库方案里，扫码只负责微信登录；AIWC 随后仍需要取得或复用本地解密材料。不要把自动登录字段、机器人 Token 和 WCDB 口令合成一种“微信 Key”。

自动鉴权的静态调用链为：读取候选函数 `0x46682e8` 在 `0x4668758` 取字段名指针，经 `0x452f7a8` 包装器调用 `0x5700494`；写入候选函数 `0x466922c` 经 `0x452fe7c` 调用 `0x57002b4`。这些是静态读写证据，尚未证明字段的有效期、加密方式、对应账号和服务端验签规则。没有必要为了读取已打开的本地库而先复刻这套登录协议。

## 3. 本地数据库密钥的实际生命周期

以下地址都是该摘要对应 arm64 切片的未加 ASLR slide 虚拟地址，只能用于这个版本的定位；不是固定运行地址，也不能跨版本直接复用。

### 3.1 数据库上下文能识别，密钥并非只在登录瞬间存在

`0x58bb370` 分配 0x88 字节的 codec 上下文、克隆密码学 provider，并建立两个 0x28 字节的读写子上下文。限定指令范围确认了下列字段：

| 对象 | 偏移 | 静态含义与验证用途 |
|---|---|---|
| codec | `+0x0c` / `+0x10` / `+0x14` / `+0x18` / `+0x1c` | salt 长度、key 长度、IV 长度、block 长度、page 大小；本次识别值为 16 / 32 / 16 / 16 / 4096 |
| codec | `+0x68` / `+0x70` | 两个读写 cipher 子上下文指针 |
| codec | `+0x78` | provider 表指针；探针额外校验 KDF 与 AES 回调均指向当前业务库的已分析函数 |
| cipher 子上下文 | `+0x04` / `+0x18` | 输入口令长度与经过混淆的口令缓冲区 |
| cipher 子上下文 | `+0x08` / `+0x10` | 经过混淆的派生加密密钥与 HMAC 密钥缓冲区 |
| cipher 子上下文 | `+0x20` | keyspec 缓冲区；本轮没有把它作为生产获取入口 |

`0x58ba638` 对输入口令先复制、再按 32 字节静态掩码循环 XOR。`0x58bc598` 的 KDF 分支经 provider `+0x30` 派生加密密钥，随后也处理混淆。`0x58bb830` 的页面处理路径先还原 `cipher+0x08/+0x10` 的材料，再经 AES/HMAC 回调读写页面，最后重新混淆。研究探针只在自己内存中还原，不调用微信的还原函数。

`0x58bc494` 在其条件分支下，对两个子上下文的口令缓冲区填入 `0xff`，释放，并将指针和长度清零（具体清除指令位于 `0x58bc53c..0x58bc584`）。这解释了为什么只扫描裸 32 字节口令或文本 keyspec 容易失败。清除分支受 codec 状态控制，不应表述成所有上下文始终都会清除。

运行验证找到了 **124 个 provider 回调也匹配的 codec 候选**；检查的 248 个读写子上下文中，246 个口令指针或长度为空，没有发现长度为 32 的保留口令。另一方面，混淆的派生密钥仍然可用。不能据此断言微信所有内存里都不存在原始口令，但足以否定“读取只能等下一次登录”的工程前提。

### 3.2 当前版本确实注册了 CommonCrypto KDF

`_CCKeyDerivationPBKDF` 导入 stub 为 `0x7138d60`。包装器 `0x58ba0cc` 分 SHA1 / SHA256 / SHA512 分支调用它；`0x58b9ec8` 将该包装器写到 provider `+0x30`，AES 包装器 `0x58ba1a8` 写到 `+0x38`。默认 provider 指针位于全局 `0xa4e8c20`。

只读运行探针确认当前加载库 UUID 匹配、默认 provider 已初始化，KDF 回调指向 `0x58ba0cc`。这是运行中的函数指针事实，**没有观察登录事件调用该函数**。

现有文档中“4.1.13 的 LLDB 断点未触发”属于过去一次版本/环境观察，不能推出 4.1.15 没有 CommonCrypto KDF，或所有登录方式一定不经过它。当前版本的注册证据也不能反向证明 4.1.13 的调用链。

### 3.3 现有登录 helper 截获的是输入，且会改变目标调试状态

REA 与小范围完整反汇编确认：`wechat_xkey_helper` 查找 `CCKeyDerivationPBKDF`，使用 ptrace、代码断点写入和线程 debug 状态，在命中后检查输入寄存器所表示的口令长度等于 32，读取输入口令。它没有实现二维码协议或服务端鉴权，也不是只读扫描工具。

它取得的是 **PBKDF 输入口令**，不是输出派生密钥。若调用使用文本直连形式、没有经过该函数、发生在挂钩之前，或命中的是别的业务调用，就不能按“hook installed”判定数据库已解锁；必须对目标数据库验证。

本轮没有运行这个 helper 的挂钩能力。生产常规「连接」流程应优先使用下面已验证的只读路径；需要改变调试状态或重启微信的操作应成为单独说明的兜底动作。

## 4. 无需重新登录路径的验证结果

研究探针按以下顺序工作：校验目标库身份 → 遍历有驻留页面的可读写堆类区域 → 识别 codec 尺寸与回调结构 → 读取子上下文中混淆的派生材料 → 在探针内存中还原 → 对目标库的加密页验证 → 清理临时缓冲区 → 只输出布尔结果。

最终结果来自 `live-codec-masked-derived-account.json`：

| 数据库类别 | 首页 AES/SQLite 结构 | 首页 HMAC | 第二页、末页 HMAC |
|---|---|---|---|
| session.db | 通过 | 通过 | 通过 |
| contact.db | 通过 | 通过 | 通过 |
| message_0.db、message_1.db、message_2.db | 全部通过 | 全部通过 | 全部通过 |
| biz_message_0.db、biz_message_1.db、biz_message_2.db | 全部通过 | 全部通过 | 全部通过 |
| message_resource.db | 通过 | 通过 | 通过 |
| hardlink.db | 通过 | 通过 | 通过 |

这次读取扫描块约 720.9 MB，耗时 **0.435 秒**；扫描数包含块边界重叠。provider 匹配的上下文有重复读写材料，66 次首页材料匹配不等于 66 把不同密钥。每个通过校验的派生候选最多对应这 10 个目标中的 **一个**数据库；没有找到可用于全部目标的 32 字节原始口令。

页面参数由合成测试和真实页 HMAC 共同支持：4096 字节页，16 字节 salt，80 字节 reserved（IV 16 + HMAC-SHA512 64），AES-256-CBC；HMAC key 由 AES key 与 `salt XOR 0x3a` 经 PBKDF2-SHA512 两轮派生，覆盖密文、IV 和小端页号。PBKDF2-SHA512 256000 轮的原始口令分支通过合成测试和静态 KDF 链确认，但本轮真实成功结果使用 `direct` 派生材料，没有重新验证实际账号原始口令的派生次数。

**适用条件与限度：**

- 本机 SIP 已关闭，debugger 签名的研究探针取得 `task_for_pid` 成功；普通未签名 Python 探针返回拒绝代码 5。尚未验证 SIP 开启、普通发布签名、不同 macOS 权限组合的可用性。不能承诺只勾选「开发者工具」就一定成功。
- 只验证当前版本、当前运行状态、一个账号已被微信打开的 10 个数据库。不是完整历史查询、schema 适配、WAL 一致性、图片解密或所有数据库的端到端验证。
- 不证明数据库重建、切换账号、微信退出、进程重启后这些内存材料仍存在，也没有验证所有版本共享同一结构。
- 当前拿到的是每库派生材料。底层可能曾使用同一账号口令，再结合各库 salt 派生；本轮没有恢复其来源，所以不能说原始口令必然“一库一把”。
- 起初线性扫描约 4 GiB 没有命中，原因包含扫描预算先消耗在非堆区域。递归遍历保留深度、优先驻留堆类区域后才定位成功；不应把初期失败写成“内存里不存在”。最终筛选也只是有界扫描策略，生产版需处理漏选区域与并发变化。

## 5. 对 AIWC 的具体接入方案

### 5.1 用户看到一个「连接微信」流程

1. 自动发现账号目录；多个账号时让用户明确选择，不能把“最近修改目录”当作登录身份。已有凭据按所选账号查询、解密并对当前数据库验证。
2. 已有可用凭据时直接打开本地数据。已有的「进入」点击同时控制自动回复、监控、定时任务和手机通道启动；取消这道页面门槛时须单独明确这些服务的启动策略。
3. 首次连接由用户点击发起只读获取。先检查权限和版本，再一次收集当前可用的每库材料，匹配所选账号的数据库；微信未登录时提示先完成微信自身登录，登录后只读重试。
4. 数据库凭据验证成功立即加密保存、打开文字聊天。图片作为随后补齐的独立能力，失败或取消不撤销已经验证保存的数据库连接。
5. 若部分分片没有打开过、没有匹配材料，明确返回哪些读取能力未就绪；不能显示空聊天假装读取完整。用户之后主动「补齐连接」时重扫；普通 SQL 查询不隐式访问进程。
6. 权限不足返回 `needsAuthorization`；超时返回超时；版本不支持返回版本限制。登录时截获、重启捕获、手动密钥输入留在高级诊断，分别说明前提与影响。

「顺滑」来自常规成功路径短、已完成部分立即可用、错误可以照做，不是隐藏授权要求或自动重启微信。

### 5.2 从一把账号密钥扩展到账号内的数据库凭据集合

当前 [dbKeyResolver.ts](../packages/substrate/src/key/dbKeyResolver.ts) 与 `createBridgeQuery(bridge, keyFor)` 已有按数据库取密钥的接口。可以扩展现有解析器，接入用户明确发起获取后返回的已验证材料；无需复制另一套读取引擎。

建议由 protocol schema 定义版本化凭据集合，包含账号归属、规范化的库相对位置、数据库 salt、密钥形式 `raw/direct` 和对应材料。集合整体只存目标账号的 `secretStore`；普通配置只存引用和不含密钥的凭据修订号。渲染层只获得能力状态、数量、错误码，私有集合不能通过通用 `secret:reveal` 返回页面。

数据库 salt 或文件身份变化时先验证，不复用旧密钥；材料按账号与库隔离，reader 关闭时清理缓存。成功取得一个库的材料，只代表该库可读。要支持微信关闭后读取联系人与历史分片，必须把对应各库已验证材料一并加密持久化，不能只存 session.db 那一把。

现有 `liveKeyCandidates.ts` 只实现 Windows 候选收集，macOS 返回空数组；其“macOS 一把账号口令足够”注释不能覆盖本次恢复每库 `direct` 材料的路径。应改为注入已验证凭据集合；新增 Mac 收集器作为 substrate utility process 中的可取消、有限时只读能力，用户点击连接/补齐时启动。

研究探针不是可直接打包的 helper：只输出布尔值，没有生产 IPC、完整 schema、账号选择、版本适配表、取消协议和读取器集成。正式实现应保留源码与许可证，列明构建和哈希，并覆盖每个打包架构。现有两个 Mac helper 的源码来源与构建复现仍未补齐。

`scope: 'image'` 的确不获取数据库密钥，但 `acquireImageKeys` 可以为图片 AES 发起内存扫描。因此“只读扫描不碰进程”“图片获取完全不碰微信进程”都是过宽的说明，应改成“不挂钩、不重启；图片扫描也可能需要进程访问权限”。

## 8. REA 生产接入与验证更新（2026-10-15）

### 8.1 已实现的连接行为

REA 的常规入口已经是「连接微信」：所选账号已有可认证的保存材料时直接复用；首次连接或主动补齐只请求 `scope: database`。文字聊天不等待图片获取。启动后仅恢复上次明确选择的账号，凭据认证成功才连接并恢复该账号已配置的后台服务；恢复失败保留可操作的连接页，不自动扫描、切换账号或改变微信状态。

生产实现扩展了现有读取器：

- [wechatCredentials.ts](../packages/protocol/src/wechatCredentials.ts) 定义版本化私有每库集合、helper 结果及公开能力 schema。账号、库相对位置、salt、`raw/direct` 形式与材料经验证；集合只保存在所选账号的 safeStorage `secretStore`，配置只有引用和修订号。渲染层只看到认证数量、缺失相对路径、掩码与错误；bundle 不能通过通用密钥揭示接口返回。
- [macosCodecScanner.ts](../packages/substrate/src/key/macosCodecScanner.ts) 与 [wechat-codec](../native/wechat-codec) 接入只读 codec helper，限制版本与 provider、扫描预算、输出体积、取消及父进程存活。源文件使用本仓库 MIT，构建与产物哈希见 [native README](../resources/native/README.md)。当前 arm64 helper 只支持该 SHA-256 / UUID；x64 helper 明确返回 `unsupported_version`。
- [keyAcquireRuntime.ts](../electron/hosts/keyAcquireRuntime.ts) 与 [keyAcquireClient.ts](../electron/main/substrate/keyAcquireClient.ts) 把获取与认证隔离到短生命周期 utility。主进程确认将数据库材料写入目标账号安全存储后返回 `database_ack`；只有成功 ACK 后才完成数据库步骤或进入可选图片步骤。最终交付等待 `final_ack`，请求等待 utility 清理退出；超时、取消、父进程消失及拒绝保存均有关闭路径。
- [dbKeyResolver.ts](../packages/substrate/src/key/dbKeyResolver.ts) 只使用保存的同账号材料，检查 realpath 边界、salt 及首页 HMAC，reader 关闭擦除解析缓存。查询时扫描候选的旧路径已移除。材料不足、已保存库消失或库被替换均保持 locked；读取失败不作为“没有聊天记录”推进完整游标。
- 引导页与设置统一调用目标账号的能力查询；切换目标清除旧显示并重新查询，异步结果绑定目标与代次。数据库先认证与加密保存，图片使用独立 scope，保存图片后修订号使 reader 更新材料。登录挂钩 helper、原自动重启捕获及调用路径已删除。

Windows 显式采集目前仍返回一个 legacy Key，没有完成 Windows 每库集合采集。保存的 Key 只能用于逐库认证成功的文件，其余联系人或消息库保持 locked；不会在 SQL 查询时恢复旧的隐式进程扫描。这里不能写成 Windows 全库持久化已完成。

### 8.4 未覆盖图标库与清除行为修复（2026-10-15）

本机 24/25 覆盖的唯一缺失文件为 `third_app_icon/third_app_icon.db`。仅读取文件元数据及 SQLite 标识确认它为 12288 字节的非明文库；不能按“明文无需密钥”跳过认证。微信 4.1.15 的主要业务库 `Contents/Resources/wechat.dylib` 静态字符串中单独登记 `third_app_icon` 与 `third_app_icon.db`，与会话、联系人和消息分片命名分开。AIWC 的数据库发现、消息 / 联系人读取及媒体定位链路没有查询此库，因此该文件未解锁不影响当前实现的聊天读取；这不等于此库已解锁，也未取得其表结构。

只读 helper 依赖目标进程可识别的驻留 codec。本轮没有读取微信进程，也未证明该图标库未匹配的精确原因：库未打开、codec 不驻留或布局不符合当前适配仍是可能性。不能用其他 24 库的认证结果承诺任意磁盘库都能获取。界面保留真实覆盖数量和缺失路径，仅对这个已知辅助路径给出用途说明；消息 / 联系人缺失仍保持 locked，未知库不当作辅助库。

原 `substrate:clearKey` 在删除数据库材料后复用“凭据变更即重连”路径，重连时因材料不存在返回「尚未配置微信账号」。第一次删除已完成，IPC 却失败，界面保留旧状态；第二次因 reader 已非 ready 跳过重连才成功。修复为先关闭当前 reader，再删除材料与配置引用，一次完成；图片清除继续受控重连，其他账号清除不关闭当前 reader。自动化测试覆盖关闭失败保留材料、临时安全存储重载后的删除结果、一次危险确认完成与旧覆盖状态清理；未删除用户真实缓存作测试。
