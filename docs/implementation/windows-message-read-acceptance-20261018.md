# Windows 消息读取修复复验（2026-10-18）

## 结果与影响

原先四库 locked 的原因已证实为 Windows 主库预分配尾部被误当成有效末页，密钥并未缺失。四库中三个与消息有关；必需分片缺失时 reader 拒绝读取，因此原来的 15/19 确实不能满足聊天功能，不能以 reader ready 代替消息验收。此记录替代 [初轮记录](windows-connection-acceptance-20261017.md) 对四库原因未知及消息尚未验证的结论。

当前本机真实 Electron 首次连接为 19/19；保留旧 15/19 缓存执行补齐后为 19/19。完整退出 AIWC 后，在拒绝进程访问的测试边界下仍恢复 19/19，等待用户点击进入，8 个现有会话全部可读。没有改变微信登录状态，无需退出再登录微信。

## 修复与证据

19 库全部存在相同 99 字节混淆 keyspec 候选，认证为同一 SQLCipher 4 页格式的 direct 材料。四个原误锁库的物理容量为 6400、6400、12800、6400 页，首页经 AES 与 HMAC 认证后声明有效页数分别为 47、42、77、24。change counter 与 version-valid-for 相等，第二页及有效末页 HMAC 通过，其余预分配尾部全零。[匿名逐库证据](windows-preallocated-databases-20261017.json) 不包含凭据、salt、指纹、账号或聊天内容。

依据 [SQLite 有效页数规则](https://sqlite.org/fileformat2.html#in_header_database_size)，共享 helper 仅信任已认证、非零、计数有效且不超过物理容量的逻辑页数；零或过期页数回退物理容量，非整页或越界拒绝。扫描器采样逻辑末页，副本逐页认证并解密整个有效范围，再叠加已认证 WAL。IV 缓存不能跳过有效页认证，同 IV 页头缩小也更新副本。仅修扫描器仍会在副本路径失败，本轮两处均修复。

先加入失败测试复现预分配尾部误判及副本问题，再验证真实 SQLite 查询、源文件不变、有效页损坏拒绝、过大 / 过期 / 零页数、同 IV 篡改与页头更新、WAL 增长 / 收缩和空源清除旧明文副本。没有放宽页认证，没有为每库重复扫描微信进程。

## 保留的边界

- 17 库的额外 SQLite integrity_check 为 ok；两库为 FTS5 搜索库，标准 SQLite 的该指令返回 ERR_SQLITE_ERROR / SQL logic error。两库的完整有效页认证、解密及 schema SELECT 均成功，但本轮没有证明其 integrity_check 失败的根因，不将其算作结构检查通过。主聊天分片没有该失败。
- 原始七张消息表共 117 行；其中一张单行表对应会话库中被既有 shouldKeepSession 系统 / 通知规则过滤的身份，已用同一元数据的映射核实，未输出名称或标识。8 个正常展示会话的源 reader 与应用接口均为 116 条；这一差异不是普通聊天漏读。仍不声称覆盖账号曾经存在的一切历史或已删除会话。
- Windows WCDB 对象偏移、创建 / 销毁路径、跨微信登录生命周期及其他客户端版本仍未证实。未挂调试器、注入、写进程、提权、改变微信文件或登录状态。
