# 后台微信回复：computer-use-reply

## 当前行为与未完成项

本分支普通 `npm run dev` / 生产构建默认使用后台专用发送器，**不会退回前台快捷键发送**。旧的 `AIWC_WECHAT_SEND_MODE` 开关不再参与选择。`main` 不受本分支修改影响。

**尚未交付可用的 Codex 式后台回复。** 默认禁止抢焦点是一项约束，不等于已经实现静默发送。

2026-09-09 真机检查：

- 辅助功能权限已通过，微信版本为 4.1.13。
- 两个窗口的 AX 子树合计只有 14 个节点，没有可写聊天输入框；菜单栏的搜索输入不算聊天输入框。
- Codex Computer Use 选中“搜索聊天记录”子窗口，截图为空白；按窗口 ID 独立捕获主微信窗口得到纯黑图。
- 没有在无法验证的界面里输入内容，也没有发送测试消息。

这些证据表明当前纯 AX 方案不可用，但尚不能排除进程/窗口定向事件结合截图验证的方案。需要先恢复可读的微信主窗口，进行无发送的验证；若仍无法可靠控制，再评估独立桌面/设备。

## 启动和诊断

```sh
npm run dev
npm run background-reply:inspect
```

`predev` / `prebuild` 自动编译当前 macOS 架构的 Swift 辅助程序至 `resources/native/darwin-<arch>/aiwc-background-helper`，该二进制由 Git 忽略，打包通过现有 extraResources 复制。没有安装 Swift 工具链会明确构建失败。非 macOS 不编译，发送器仍不会使用前台回退。

只读诊断返回版本、窗口节点数量、窗口内有无可写输入、控件角色/标识/动作。不返回聊天内容、联系人名或草稿。发送动作只使用 AX 控件；显式运行的按键实验可以向微信进程发送固定快捷键，不激活应用、不移动鼠标、不发送全局键盘事件、不写剪贴板。

选择会话前先诊断：当前版本没有可写聊天控件时明确返回“静默发送不可用，未唤起微信”。即使提供了配置，也不能绕过能力检测。

若未来版本暴露控件，经过验证的配置默认置于 `<userData>/aiwc/background-reply/profile.json`，可用 `AIWC_WECHAT_AX_PROFILE` 指定替代路径。配置需包含实际微信版本和 conversationList、conversationRow、header、composer、sendButton 的 role / identifier。当前版本没有这些控件，不提供虚构配置。

## 发送边界

- 目标只在现有列表中按完整名称唯一匹配，并复核标题；未实现稳定 wxid 匹配，同名会话不能用于正式自动发送。
- 不覆盖现有草稿；写入后与发送前核对文本。
- 用户在用微信或前台变化时停止；选择阶段最多短暂重试两次，并非无限排队。
- 仍需数据库回读确认，失败即暂停。AX 不重复结果不确定的发送动作。
- 用户操作与 AX 检查不是原子事务，后台事件或 AXPress 是否引起焦点变化必须真机验证。

## 验证

新增默认启动回归：不设置环境变量、旧值为 foreground、旧值为 background-ax、非 macOS，均不能落入旧全局输入发送器。新增窗口控件缺失和权限失败测试，保证不执行选择/写入。

## 2026-09-09 生成失败修复

用户报告 13:49 开始的回复生成失败，日志在 13:50:16 记录通用错误，耗时约 45 秒。原逻辑将 length、aborted、content_filter、error 全部折叠成同一句文案，没有记录原始结束原因，所以无法据旧日志断定该次失败的唯一原因。

发现并修正自动回复固定 1800 输出 token 的限制：默认 8192，只有 length 才从头重试一次至最多 16384，并遵守模型配置的更低上限。思考过程也会占输出额度；不将截断正文交给发送器。新增完成状态校验、分原因错误文案及不含正文的模型/用量/结束原因日志。

使用用户已配置的 deepseek-v4-pro 和虚构的“明天见”输入进行了真实 API 检查：旧额度的一次请求正常结束，消耗 757 输出 token，其中 754 为思考，因此未复现截图中的同一次失败。修改后的完整生成函数也正常结束（stop，68 输出 token，其中 65 为思考），没有调用微信发送器。测试脚本和凭证均未提交。

生成、监测、发送、模拟桥接共 73 项回归通过；定向 ESLint、类型检查、生产构建通过。另补齐基线 INVOKE_CHANNELS 中漏登记的 clone:notes / clone:deleteNote / clone:reflect，避免分支独立构建失败。


## cua 分支：窗口捕获检查

从 main 的 be3de0c 创建 cua；后续实验在 cua 上进行。只读探测新增 windowSharing 和 screenCapturePermission，不再把窗口截图失败归结为辅助功能权限。

真机微信 4.1.13：录屏权限为 true，但唯一主窗口的 kCGWindowSharingState 为 0。系统 screencapture 按窗口 ID 捕获失败，ScreenCaptureKit 得到纯黑图，Codex Computer Use 得到空白图；设置窗口可以正常截图。

已实际检查微信设置 → 通用和显示菜单。通用 → 功能下的“点击截图按钮时保留当前窗口”已开启，此项针对微信自带截图行为，不能当作第三方窗口捕获授权。没有找到可以永久解除主窗口捕获限制的公开开关，也没有修改任何微信配置、权限或进程。窗口共享状态是诊断事实，不证明存在某个用户可以关闭的“防截屏”选项。

新增测试保证窗口不可捕获时不盲目输入，且未知状态不误报截图排除。**本轮仍未实现后台发送，不可将诊断改进当作功能完成。**

## cua 分支：进程定向按键实验

新增两个手动诊断入口，不接入自动回复：

- `npm run background-reply:probe-settings`：微信在后台且设置窗口未打开时，向微信 PID 发送 ⌘,。检测新设置窗口，再通过该窗口的关闭按钮关闭它。
- `npm run background-reply:probe-input`：仅向后台微信发送 ⌘F。不输入文字，不按回车；可能改变微信内部焦点，不自动还原搜索状态。

微信在前台时拒绝诊断；设置已经打开时不操作现有设置窗口。诊断只返回行为元数据，不记录联系人或消息。`ok` 表示诊断执行结束；只有 `targetEffectVerified` 才表示观察到目标界面的预期变化，不能把事件投递当作输入成功。

实测：设置探针一次观测到新设置窗口并成功关闭，操作前后的前台应用相同、剪贴板计数不变。该次鼠标位置不同，不能区分用户移动和其他原因，因此未认定“零干扰”验证通过。⌘F 实验前后前台、鼠标、剪贴板相同，但搜索焦点未能读取，效果仍未验证。前后采样不证明操作期间没有短暂焦点变化。

另做本地只读实验：通过 SkyLight 的 `SLSHWCaptureWindowList` 对唯一微信主窗口使用默认和高清捕获选项，两次均无图像；读取应用的 `AXFocusedUIElement` 也没有返回控件。没有修改微信进程、系统保护或发送消息。实验截图、参考仓库、临时脚本不提交。

结论：后台快捷键有实际响应，但尚未验证聊天选择、中文输入、草稿核对及发送闭环。当前不能交付为可用的后台回复。下一条候选路线是独立桌面/设备，先验证微信登录和输入隔离，再接入 AIWC；虚拟机尚未安装，兼容性尚未验证。

参考接口来源：[Control Room 的窗口捕获声明](https://github.com/dev-jonghoonpark/control-room/blob/main/Sources/CGSPrivate/include/CGSPrivate.h)、[WebKit 对窗口硬件捕获的使用](https://bugs.webkit.org/show_bug.cgi?id=277572)。这些项目的支持情况不代表微信一定可用。
